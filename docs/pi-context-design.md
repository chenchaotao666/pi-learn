# Pi 上下文设计与策略

本文说明当前 `packages/coding-agent` CLI/SDK 的上下文设计，基于源码静态核实。`packages/durable` 有独立实现，不应直接套用本文流程。实际行为可能受模型配置和扩展影响。

核心策略：**完整历史持久保存，每次请求从当前分支生成模型上下文；接近窗口上限时，用旧历史摘要替代较早消息，保留近期原文。**

## 1. 三种不同的上下文

长任务既需要完整记录，又不能无限增加模型输入。因此 Pi 将历史存储和请求内容分开。

| 层次 | 内容 | 用途 |
|---|---|---|
| 原始历史 | 用户消息、模型回复、工具结果、分支、压缩记录、上下文编辑等 | 保存、回查和恢复会话 |
| 当前会话投影 | 当前分支经过压缩与编辑后有效的消息 | 决定当前模型可见历史 |
| 模型请求 | 投影经过扩展处理、消息转换和 Provider 适配后的内容 | 实际发送给模型 |

“投影”指从完整记录中按规则计算当前应让模型看到的内容。例如，文件中有 100 条记录，当前分支经过 60 条；压缩后，模型可能只看到一份摘要和最近 15 条消息。其余记录仍在磁盘上，但不会自动参与这次推理。

## 2. 会话树决定历史范围

会话以追加式 JSONL 保存，每条记录用 `id` 和 `parentId` 表示关系。当前位置称为 leaf，即当前分支末端。

```text
A：用户提出任务
└─ B：分析问题
   ├─ C：尝试方案一
   │  └─ D：发现方案一失败
   └─ E：改用方案二
      └─ F：当前所在位置
```

当前在 F 时，历史路径是 `A → B → E → F`，不会自动混入 C、D。

重建上下文时，Pi 从当前 leaf 沿 `parentId` 回溯到根，再按时间顺序处理当前路径。这样，回到历史节点重新尝试时，既保留原有过程，又避免两条路线互相干扰。

切换分支时，可以选择生成分支摘要，将离开分支上的经验带到目标分支。例如把“方案一因接口限制失败”的结论带入方案二，而不携带整段尝试过程。

## 3. 系统规则与按需加载

除了聊天历史，模型还需要行为规则、工具定义和项目约束。Pi 将系统提示词组织成多个部分：

- 默认行为规则或自定义前言。
- 追加的系统指令。
- 项目上下文文件。
- 技能目录。
- 当前工作目录。

不同资源采用不同加载策略：

| 资源 | 如何进入上下文 |
|---|---|
| 被发现并加载的项目规则文件 | 正文进入系统上下文 |
| Skills | 通常先提供名称、描述和文件位置，匹配任务后读取正文 |
| 项目代码 | 通过读取、搜索等工具按需获取 |
| 工具定义 | 作为模型可用能力的声明参与请求 |

项目规则加载包含全局 agentDir，以及从文件系统根目录到 cwd 的祖先目录。每个目录选择第一个可读候选，顺序为 `AGENTS.override.md`、`AGENTS.md`、`AGENTS.MD`、`CLAUDE.md`、`CLAUDE.MD`，并处理去重及嵌套 worktree 情况。

技能目录不是所有 `SKILL.md` 正文的集合。默认先提供索引，再提示模型按任务读取相关技能；设置了 `disableModelInvocation` 的技能不进入模型可调用目录。

这种按需加载避免启动时把整个代码仓库和全部技能正文装进有限的窗口。

## 4. 每次请求如何生成

整体流程如下：

```text
完整会话记录
  → 选择当前分支
  → 应用最新压缩记录与 context_edit
  → 当前会话投影
  → transformContext：扩展调整消息
  → convertToLlm：内部消息转换为模型消息
  → normalizeContext：规范化上下文
  → Provider 适配
  → 模型请求
```

`transformContext` 允许扩展筛选、补充或调整请求消息。`convertToLlm` 将 bash 执行记录、自定义消息、分支摘要和压缩摘要等内部类型转换成模型可接受的消息；被标记为不进入上下文的 bash 执行记录会被跳过。

请求时的扩展转换通常不等于持久编辑。扩展 `context` 处理影响请求投影，而 `context_edit` 写入会话，影响后续上下文重建。

## 5. 压缩触发条件与预算

默认配置：

```json
{
  "compaction": {
    "enabled": true,
    "reserveTokens": 16384,
    "keepRecentTokens": 20000
  }
}
```

触发公式为：

```text
contextTokens > contextWindow - reserveTokens
```

例如，假设模型窗口为 128,000 tokens：

```text
128,000 - 16,384 = 111,616
```

估算上下文超过 111,616 tokens 时触发压缩。`reserveTokens` 为后续响应留出空间，也影响摘要输出预算；它不是仅用于阈值计算的参数。

Pi 会在新用户请求前，以及工具执行结束、需要继续下一次模型响应等边界检查预算。用户也可以执行 `/compact [instructions]` 手动压缩，并指定摘要重点。不同模型可以通过 `compaction.modelOverrides` 使用不同预算。

### Token 数量如何计算

Pi 优先使用最近有效的模型 usage，再加上后续消息的估算。如果没有可用 usage，或后续上下文编辑、压缩使旧 usage 不再适用，则估算当前投影。

文本估算主要使用 `ceil(chars / 4)`，图片采用固定近似值；系统工具声明、模型 thinking 和工具参数等也参与相关估算。这不是每次调用精确 tokenizer 的计数方式。

因此，阈值检查不能保证完全避免窗口溢出，需要配合溢出恢复。

## 6. 压缩保留什么

压缩前后可以理解为：

```text
压缩前：
系统规则 + 早期讨论 + 中期操作 + 最近消息

压缩后：
系统状态快照 + 历史摘要 + 最近消息原文
```

处理步骤：

1. 从当前投影末尾向前累计 token，寻找近期保留区间。
2. 在预算附近选择合法消息边界。
3. 将更早的消息整理成摘要；存在上一份摘要时，一并更新。
4. 追加压缩记录，保存摘要和 `firstKeptEntryId` 等信息。
5. 重建后续请求的上下文。

`keepRecentTokens = 20000` 是近期保留预算，不是精确截取长度，也不是保留固定条数。切点需要满足消息结构约束，尤其不能把工具调用与其结果拆开。例如，不能让保留区间直接从一个缺少对应调用的 `toolResult` 开始。

如果一个用户任务跨度很长，切点可能落在任务中间。Pi 会区分旧历史与当前任务的早期部分，生成相应摘要，再与保留的后半段原文组合。

摘要通常包含：

- 用户目标。
- 约束与偏好。
- 已完成、进行中和受阻的工作。
- 关键决策及理由。
- 下一步。
- 继续任务需要的重要信息。
- 已读取、已修改的文件路径。

摘要生成本身也控制输入体积：序列化时省略 thinking，工具结果截断到约 2,000 字符。该限制针对摘要输入，不代表普通工具结果在所有请求中都统一限制为 2,000 字符。

第二次压缩会结合上一份摘要和新进入压缩范围的消息，继续更新任务状态。

## 7. 压缩不删除原始历史

Pi 追加压缩记录，而非物理删除旧消息。因此，会话文件不会因为压缩而自动变小。

压缩记录包含摘要、保留区间起点、压缩前 token 数量、usage 等信息，还保存当时合并后的系统消息快照，其中包含系统提示词和工具声明状态。

系统快照解决的是恢复问题：如果某个工具在早期注册，而注册记录随后被压缩范围覆盖，仅保留自然语言摘要不足以可靠恢复工具状态。重建时，Pi 重放该快照，并排除保留区间中的旧系统消息，避免重复恢复过时状态。

### context_edit 的作用

`context_edit` 是追加式上下文修改：

- `replacement: null`：让目标消息不再进入未来上下文。
- 提供替换内容：保留原角色和其他字段，仅替换模型可见内容。
- 同一目标有多个编辑时，当前路径上最后一个生效。

例如：

```text
原始历史：
用户请求 → 失败尝试 → 上下文编辑 → 成功重试

后续模型输入：
用户请求 → 成功重试
```

失败记录仍可回查，但不会继续干扰模型。编辑只在其所属分支路径上生效；回到编辑之前的历史位置，原内容可以重新可见。

## 8. 溢出恢复与扩展能力

当 Provider 明确报告上下文溢出，或者发生可恢复的长度终止时，Pi 可以省略失败尝试，压缩后重新请求。CLI 对这种 compact-and-retry 恢复设有一次限制，避免无限循环。

已成功完成、但 usage 显示超出预算的响应可以触发压缩，不会因此重放已经完成的响应。普通 API 重试与上下文溢出恢复是不同机制。

扩展可以使用 `session_before_compact` 取消压缩或提供自定义摘要，例如调整摘要结构、保留特定业务状态，或使用另一模型生成摘要。扩展也可以在请求阶段调整上下文，因此实际运行策略应结合已启用扩展理解。

## 9. 一个完整例子

假设用户要求修复某个模块：

```text
1. 加载项目规则与技能目录。
2. 用户提出修复任务。
3. 模型搜索、读取相关代码；工具结果进入会话。
4. 模型修改代码、检查结果；历史逐步增长。
5. 预算接近阈值，较早讨论与操作被整理成摘要。
6. 系统状态快照、摘要、最近消息组成新的模型上下文。
7. 模型继续完成任务；需要早期精确细节时重新读取资料。
```

如果中途回到旧节点尝试另一方案，后续上下文沿新分支生成。需要携带旧方案经验时，使用分支摘要，而不是默认混入所有分支历史。

## 10. 设计取舍

| 设计 | 收益 | 代价或边界 |
|---|---|---|
| 原始历史与模型输入分离 | 历史可回查，请求体积可控制 | 保存过的信息不一定仍被模型看到 |
| 当前分支投影 | 不同尝试互不混杂 | 跨分支经验需要显式携带 |
| 旧历史摘要＋近期原文 | 长任务可持续，近期细节保留较好 | 摘要有损，早期精确细节可能丢失 |
| 技能和代码按需加载 | 减少无关输入 | 依赖模型正确选择并读取资源 |
| 预算估算＋溢出恢复 | 控制成本并处理误差 | 无法保证所有请求都提前避开溢出 |
| 请求扩展与持久编辑分开 | 支持临时定制和可恢复修改 | 理解实际输入需要查看多个处理阶段 |

Pi 当前 CLI 的默认主线是“分支化会话记录、请求时投影、按需加载、增量摘要压缩”，不是向量检索式长期记忆。原始历史仍在磁盘上，不等于模型永久记住其中所有内容；需要精确资料时，应重新读取或检索。
